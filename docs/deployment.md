# Deployment preparation

Castloop has been exercised in an isolated Cloudflare test installation, with important checks still outstanding. Follow [verification](verification.md); the configuration below describes the implementation rather than a production deployment guarantee.

Create separate management and delivery R2 buckets. Keep `r2.dev` access disabled. Bind both buckets to the management Worker; bind only the delivery bucket to the delivery Worker. The optional custom domain is attached to the delivery bucket, with Cloudflare cache rules for the public podcast paths and no caching of error responses. Configure an incomplete-multipart lifecycle; do not expire completed accepted objects. A custom domain makes its public podcast objects accessible through that domain, so the delivery bucket must contain only intended public material.

Set the actual account ID, bucket names and initial workers.dev delivery origin in `packages/worker/wrangler.jsonc`. Configure `packages/delivery/wrangler.jsonc` to bind the same delivery bucket, and configure the same account and bucket names in `packages/worker/wrangler.copier.jsonc`. Keep the internal service bindings and the SQLite Durable Object migration in place. Management and delivery refer to each other by service binding; the following ordering was exercised with newly named Workers and freshly created isolated test buckets:

1. Deploy minimal, route-free placeholder Workers under the intended management and delivery names. Their only handler returns HTTP 404 and has no bindings or secrets.
2. Deploy the private copier with its bucket names, account ID and R2 copy secrets. Do not give it a public route.
3. Replace the management placeholder with the configured management Worker, including its Durable Object migration, self-referencing notifier, delivery and copier bindings, and `ADMIN_TOKEN` secret. The management Worker must not expose an unauthenticated management API.
4. Replace the delivery placeholder with the configured delivery Worker and its routing service binding. Enable the intended workers.dev endpoints, then verify authentication and a synthetic Show and Episode before use.

Use temporary Wrangler configurations for the placeholders so their names exactly match the final service bindings. Automated account provisioning and other secret-provisioning workflows have not been tested. Never put secrets in the placeholder source or commit the temporary configuration files containing them.

An active Show Durable Object may continue running the previous deployment and its bindings after a new Worker version is deployed: Cloudflare's default [code update strategy](https://developers.cloudflare.com/durable-objects/deployments/durable-objects-code-updates/) is deferred, with a maximum delay of five minutes. Keep service interfaces compatible during that period. In a disposable test where an immediate reset is acceptable, Wrangler can use `--durable-objects-code-update-mode immediate`; this can interrupt an active operation and is not a normal deployment requirement.

Keep credential purposes separate:

- The CLI uses an R2 S3 API access key restricted to the management bucket, with the object operations required for reading, listing, uploading and explicit cleanup. Its `admin_token` matches the management Worker's `ADMIN_TOKEN` secret.
- The private copier Worker uses `CASTLOOP_WORKER_R2_ACCESS_KEY_ID` and `CASTLOOP_WORKER_R2_SECRET_ACCESS_KEY` for server-side promotion. Restrict the associated R2 credential to reading the management bucket and writing the delivery bucket as far as the available R2 permission model allows. The management Worker does not need these secrets.
- For custom-domain cache purge, set `CUSTOM_DELIVERY_BASE` to the same HTTPS origin in both Workers, set `CUSTOM_ZONE_ID` in the management Worker, and store `ZONE_PURGE_TOKEN` as a Worker secret with the minimum applicable zone cache-purge permission. Do not give this token to the CLI.
- Email is optional: configure `EMAIL_FROM` and `EMAIL_TO`. For the free-plan path, enable Email Routing on the sender domain and verify the administrator's destination address; sending to verified routing destinations is free. Configure the `EMAIL` binding with `destination_address` set to that single destination, replacing the unrestricted template. The sender must belong to the routing domain. Empty sender or destination leaves notifications unconfigured. Other recipient arrangements may require Email Sending and a paid plan. A send success indicates provider acceptance, not confirmed inbox delivery. See [routing destinations](https://developers.cloudflare.com/email-service/configuration/email-routing-addresses/) and [send binding restrictions](https://developers.cloudflare.com/email-service/configuration/send-bindings/).

## Credential and permission inventory

The following is the proposed least-privilege configuration for the current implementation. The isolated installation has so far been tested with broader credentials; the narrower grants and denied access must be verified before describing them as proven. Do not change an existing installation's credentials until replacements have been tested.

| Principal or credential | Required access | Scope and purpose |
| --- | --- | --- |
| CLI R2 S3 credential (`CASTLOOP_CLI_R2_*`) | R2 **Object Read & Write** | Management bucket only: list, read, upload, multipart upload, same-bucket copy and delete staged or explicitly cleaned-up objects. It does not need access to the delivery bucket or bucket administration. |
| CLI management credential (`CASTLOOP_ADMIN_TOKEN`) | Matching management Worker `ADMIN_TOKEN` | An application bearer secret, not a Cloudflare API token. It authorizes castloop management requests. |
| Copier R2 S3 credential (`CASTLOOP_WORKER_R2_*`) | Management bucket **Object Read only**; delivery bucket **Object Read & Write** | The same S3 credential signs a server-side copy from management to delivery. Its intended policy grants only source read and destination write; R2's destination write permission also includes read and list. |
| Custom-domain purge credential (`ZONE_PURGE_TOKEN`) | Zone **Cache Purge** | Only the zone containing the custom delivery domain; installed as a management Worker secret. Not needed for workers.dev-only delivery. The permission is zone-wide, not limited by this application to its hostname. |
| Wrangler deployment credential (`CLOUDFLARE_API_TOKEN`) | Worker deployment and, when needed, resource provisioning | Used by the administrator for setup and updates, not by the running CLI or Workers. Exact permissions depend on whether resources already exist and remain to be verified with a restricted token. |

R2's object-level permissions are for its S3-compatible API; they do not authorize the Cloudflare REST API used by Wrangler. Object Read & Write includes deletion, so the CLI key can delete any object in its scoped management bucket outside castloop's application-level cleanup checks. Bucket creation, deletion and configuration are administrative operations and are not required by either runtime S3 credential. See [R2 authentication and permission groups](https://developers.cloudflare.com/r2/api/tokens/).

The dashboard's R2 token flow selects a permission and one or more buckets. A single selection of Object Read & Write for both buckets is a simpler fallback, but grants the copier write/delete access to the management bucket. Cloudflare documents [multiple policies per token](https://developers.cloudflare.com/fundamentals/api/how-to/create-via-api/) and separate bucket-level `Workers R2 Storage Bucket Item Read` and `Workers R2 Storage Bucket Item Write` groups. Two allow policies, each restricted to its own bucket, are therefore a candidate for the preferred copier credential. Whether this can be created in the available dashboard flow, and whether R2 CopyObject accepts the resulting combination in this account, remain unverified. Creating API tokens via the API requires separate token-management permission; do not grant that to a runtime credential.

Management and delivery Workers use R2 bindings for their respective configured buckets, and Durable Object SQLite through its binding; they do not require R2 S3 keys for these accesses. The management Worker binds both buckets, while the delivery Worker binds only the delivery bucket. A binding is a capability available to its Worker, not a substitute for constraining who can deploy or modify that Worker. The mail binding and verified destination do not require an additional runtime API token. For custom-domain cache purges, Cloudflare specifies [Cache Purge](https://developers.cloudflare.com/cache/guides/invalidate-cache/) for the zone; configuring the domain, DNS or cache rules is a separate administrative task.

For deployment, Cloudflare distinguishes creating a Worker from editing an existing one: its [Workers authorization documentation](https://developers.cloudflare.com/workers/authorization/workers/) describes product-level Admin for creation and scoped Editor for existing Workers. R2 bucket creation/configuration and optional DNS, domain and cache-rule setup are separate capabilities. Wrangler's actual calls, UI/API grant names and any additional read permissions for this installation are not yet proven with minimally scoped credentials. The standard Workers token template includes permissions for services castloop does not use, so treat it as a starting template, not a minimal policy. Do not grant API-token creation, billing, KV or DNS modification merely for ordinary podcast operation.

### Verification before narrowing a live installation

Use separate disposable buckets, Workers, object keys and credentials; never test denied writes or deletions against existing content. Record permission names and results without secret values. Allow for R2 permission changes to propagate before interpreting a failure.

1. Create a CLI Object Read & Write key restricted to the disposable management bucket. Verify metadata pull/push, list, small and multipart audio uploads, same-bucket copy and cleanup of a synthetic staging object. Verify access to the delivery bucket and bucket administration is denied.
2. Create a copier key with separate source-read and destination-write policies if the account supports it. Verify a real application CopyObject and matching output bytes. Confirm writes/deletes to the source and access to an unrelated bucket are denied. If policy creation or copying fails, record the result and test the two-bucket Object Read & Write fallback separately; do not silently describe it as source read-only.
3. For a disposable custom-domain zone, test the application's prefix purge and a subsequent cache MISS using a separate zone-scoped Cache Purge-only token. Test denial against an unrelated zone only when an authorized disposable zone is available.
4. Independently test the deployment credential against already provisioned disposable resources; enumerate the exact operations and grants that succeed. Test initial provisioning separately. Keep runtime credentials separate and record any permissions or resource scopes that Cloudflare or Wrangler cannot narrow.

Never commit credentials or generated secret files. The application uses R2's beta conditional destination CopyObject extension for multipart source staging; verify it in the disposable account before relying on it.

After configuration, verify direct uploads of representative 50 MiB and 100 MiB audio, immutable create-only behavior, server-side copy, future-release alarms, full and ranged delivery, caching and purge, withdrawals, optional email and per-Show migration/rollback. Measure actual Durable Object CPU and memory for representative archives. Local test elapsed time is not evidence of Cloudflare CPU usage or free-tier capacity.
