## Disposable deployment smoke

`bun run verify:deployed` requires the explicit `--disposable` acknowledgement and does not run as part of local tests. It uploads audio and changes the specified Episode, so use only a dedicated disposable installation and Episode. Prepare a published Show with cover and a new Episode whose TOML has `publish = true` and a future `published_at`; push both metadata files first, and retain the Episode's GUID from the metadata export. Select a release time between 30 seconds and 30 minutes in the future, leaving enough time to hash and upload the file. Run from the repository root, for example:

```sh
bun run verify:deployed --disposable --workspace /path/to/disposable-workspace \
  --binary /path/to/castloop --show s-01234567 --episode e-01234567 \
  --audio /path/to/50mib.mp3 --origin https://delivery.example.com \
  --guid urn:uuid:example --release-at 2030-01-01T00:00:00Z
```

The tool verifies that the Episode initially has no public audio, uploads a valid MP3 of at least 50 MiB through the CLI, checks the feed and audio remain unpublished before the deadline, and waits up to three minutes after release for the feed, HEAD, two one-byte range responses and the complete audio checksum. It also checks suffix, open-ended and unsatisfiable ranges; when a strong ETag is present it checks matching and mismatching `If-Range`. Multiple-range status and content type are reported as observations, not treated as a compatibility guarantee. Run again with a fresh Episode and a 100 MiB or larger file. It reports elapsed time and cache headers, but does not measure Worker/DO CPU, memory, R2 operation counts, prove a cache hit, or exercise every update, withdrawal, migration or email case. Record those separately using the real account and complete the remaining checks in the design. The smoke script has only been exercised with local mocks; no deployed result is claimed.

Failure notifications use a private service binding back to the management Worker's notifier entrypoint. Set `EMAIL_FROM` to an address at a domain enabled for Cloudflare Email Sending and `EMAIL_TO` to the installation's administrator destination; leave either empty to disable mail. Configure the email binding's sender and destination restrictions for the installation before deployment. Notification tests use the local service and a mock sender; provider acceptance and a real controlled recipient still require account integration testing. Failure status is saved before sending, and a notification error does not retry publishing.

The local migration components check custom-domain HEAD, cache status and a one-byte range, validate and batch zone prefix purge requests, generate the feed for the pending origin, and only switch the Show's routing state after publication/purge. The CLI confirms migration and rollback; delivery routing reads the Show's committed origin through a private service binding. Local tests also exercise cancellation of a pending migration and withdrawing an episode using the last valid feed while migration remains pending. A local Show migration integration test exercises the publication state machine and generated feed with mocked preflight and purge responses; actual deployed behavior remains to be verified. Configure matching `CUSTOM_DELIVERY_BASE` values in both Workers, `CUSTOM_ZONE_ID` in management, and a separate `ZONE_PURGE_TOKEN` Worker secret before attempting a custom-domain migration.

The selected compatibility date is `2026-11-04`, the latest date accepted by the installed local runtime at the time of testing. Type generation and Workers tests start a local loopback server. The Worker binding declaration is generated by `bun run types:worker` and is not committed.

## Outstanding

Draft creation retries IDs that already exist in the local workspace. A new Show receiving a revision conflict is reidentified only after the CLI confirms an existing Show through its management snapshot. It moves the local Show directory, updates the Show and Episode TOML identities with original-file backups, and retries with a new operation ID. The local tests use a mock management/S3 server and also verify rollback when an Episode backup cannot be created. An uncertain response retains the original operation and IDs. Remote Cloudflare collision behavior remains unverified.

New local Show and Episode drafts also exclude IDs present in the workspace baseline or unresolved creation receipts, even when their local directories have been removed. Tests force such collisions, including a deleted baseline entry, and verify that another ID is chosen. Collision-driven ID regeneration uses the same exclusion. The local standalone-CLI integration test also forces a new Show ID to collide with an existing Show in a real local Durable Object: the CLI selects a different ID, retains the draft backup, and the original Show's revision remains unchanged. Other workspaces and external writers remain subject to the management Worker's creation and revision checks.

For an Episode create checked at the current Show revision, the Worker identifies an existing Episode ID with `identity_conflict` and the issue path `episodes.<episode-id>.id`; other identity errors and stale revisions do not carry that collision path. For a matching rejection of a newly created Episode, the CLI moves its local directory to a new ID, backs up the original TOML, rewrites the ID and retries the batch with a new operation ID. It reports the ID change, and preserves local media without copying it. Before moving either kind of draft the CLI writes a local recovery record; the next push rolls back an interrupted move before inspecting metadata. Recovery first compares every affected file against its original and rewritten bytes, and stops rather than overwriting a later edit. Tests simulate interruption, mixed file states and later edits; they do not simulate a machine power failure or filesystem durability guarantees. This assumes only one process modifies the workspace at a time. Stale-revision Episode conflicts still require pull; they are not automatically treated as collisions.

Before a metadata push, the CLI checks for saved uncertain mutation receipts for the affected Shows and directs the administrator to retry them first. Local tests verify that a second push does not submit another mutation, that retries retain the original request on an uncertain response, and that an explicitly rejected retry removes its receipt. This guard is workspace-local; it does not coordinate other computers or concurrent CLI processes.

The administrator may explicitly abandon an unresolved operation after confirmation. Local tests check that the pending receipt moves to an abandoned-record directory without overwriting an existing different record; this does not establish whether the remote operation was accepted.

The CLI also blocks workspace and remote mutations while an interrupted local ID change is unresolved. `operation recover-local` restores the files without contacting a server; `push` runs the same recovery before continuing. A standalone CLI test verifies that an audio upload is stopped before it inspects or uploads a file.

The design specifies machine-readable JSON mode for CLI outcomes. `castloop check --json` emits versioned reports including the full check result, errors and optional delivery probes; `castloop push --json` reports per-Show acceptance, delivery, uncertain receipts and local timezone normalization; `castloop operation retry <id> --json` reports acceptance separately from delivery and distinguishes uncertain responses. `show delete`, `episode delete`, `delivery migrate` and `delivery rollback` also accept `--json`, requiring `--yes` for confirmation. Show cover and Episode audio uploads accept `--json` and report uncertain operation IDs; `recover --json` returns the observed revision and result. `pull`, `show list`, `inventory`, `export`, `restore`, `restore-resume`, and `cleanup` also support JSON. Local setup and draft creation commands have human-readable output only. Do not rely on human-readable text as a stable structured interface.

CLI tests cover accepted changes with pending delivery for push, deletion, media upload and receipt retry: the accepted revision remains visible but the command exits with code 1 until delivery is complete. Human-readable output directs the administrator to check and, if necessary, recover the Show.

The standalone CLI has also been exercised against both real application Workers and their locally simulated R2 and Durable Object bindings. The local integration scenario covers metadata conflict backup, lost acceptance response and idempotent retry, invalid Show and Episode behavior (including XML-invalid characters in TOML), show and episode creation, cover and audio upload, feed and MP3 delivery, metadata and audio replacement with stable GUID, scheduled publication by a local Durable Object alarm, inventory and cleanup with active-source protection, episode/show withdrawal, and export/restore with an explicit resume. Cleanup is tested with lost claim and completion responses, including recovery of a claim from another workspace without its original receipt. To avoid waiting days, a fixture-only hook changes the local ledger's storage timestamps before cleanup. The test-only bridge emulates the S3 operations used by the CLI and R2 CopyObject, and stubs cache purge because those services are not available in Wrangler's local environment. It therefore does not verify the real S3 API, production copy, or cache invalidation. It expects `.local-test/mp3-decoder/50mib-silence.mp3` and `100mib-silence.mp3`; their local generation and inspection are described below. The bridge's multipart and copy implementation is a test adapter, not a production Worker.

MP3 inspection checks the declared audio byte count in a first-frame Xing/Info header when available, and rejects a file shorter than that declaration. When both byte and frame counts are available, it also streams the declared audio region after the Xing/Info frame through `music-metadata` and rejects a detected frame count below the declared count. This catches a locally generated Xing-tagged sample with a missing middle frame that the ordinary metadata parse accepted. It also rejects specific MPEG frame-header errors reported by the library, which can otherwise return a partial duration. Tests cover a modified frame header, a trailing ID3v1 tag containing false sync bytes, truncated and complete fixtures, and local CBR/VBR samples. Some free-format or otherwise unsupported MPEG frames, or files with inaccurate Xing counts, may be rejected. The inspection does not decode every MP3 frame or establish that all forms of audio corruption are detected.

The Xing/Info length comparison excludes a recognized 128-byte ID3v1 trailer. A local test confirms that a complete tagged fixture remains accepted while an 80-byte-short fixture with the same trailer is rejected. Other types of trailing metadata and files without a trustworthy declared size can still conceal truncation.

Inventory registration compares the requested digest with the object's stored SHA-256 metadata as well as its ETag and size; mismatched or omitted metadata is skipped rather than entered into the ledger. The local Worker test exercises both mismatches. This compares stored metadata; inventory does not download and rehash every media object.

An inventoried source can later be selected when its reference fields were stored in a different JSON property order. The Worker compares canonicalized references and still rejects different identities; a local Durable Object test exercises the inventory-to-acceptance path.

Audio of at most 16 MiB uses conditional streaming PutObject; larger audio uses multipart upload with 16 MiB parts and concurrency two into a unique attributable staging key. A streaming digest must still match the inspected file before promotion. A same-bucket copy pins the staged ETag and uses R2's [conditional destination CopyObject extension](https://developers.cloudflare.com/r2/api/s3/extensions/#conditional-operations-in-copyobject-for-the-destination-object) to prevent overwriting the selected key; this extension is currently beta and must be verified against real R2. Successful staging objects are removed; an interrupted or uncertain copy can leave an attributable version for inventory and cleanup. The mock S3 test covers changed file contents, multipart completion and create-only copy, not real R2 behavior. Configure R2's lifecycle to abort incomplete multipart uploads; never expire completed accepted versions.

During a multipart transfer the CLI handles SIGINT/SIGTERM by attempting the SDK abort and reporting the lifecycle requirement. Local mock tests exercise emitted SIGINT and actual OS SIGINT/SIGTERM in a Bun child process, verify no destination copy occurs and that the temporary signal handler is removed. A separate Linux test sends SIGINT to the compiled standalone CLI during multipart upload and verifies its JSON error and the absence of a management acceptance request. These tests use a mock endpoint; Windows signal behavior, hard termination and deployed R2 abort remain unverified.
