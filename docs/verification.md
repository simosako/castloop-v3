The application is under development. The administrator subsequently confirmed that the integration-test account uses a Free plan. The successful tests below are observations on that account, not a promise that arbitrary workloads fit the Free-tier limits or evidence of production readiness.

## Installation guide walkthrough

On 2026-11-16, the installation guide was exercised against new R2 buckets and three newly named Workers in the existing Free-plan test account. The repository was cloned from GitHub, dependencies were installed with the lockfile and the CLI was built. Wrangler created both buckets and the seven-day incomplete-multipart lifecycle rule. Configurations were generated using the guide's script, then the two placeholders, private copier, management and delivery Workers were deployed in the documented order. An unauthenticated management request returned 401 and the configured administrator token was accepted.

The CLI created a new Show, uploaded real podcast artwork and published two real MP3 Episodes. The unpublished Show draft reported its missing cover and the unpublished Episode drafts reported missing audio, while still saving the metadata; publication succeeded after the missing assets were uploaded. `check --delivery` passed. The public RSS contained two Episodes, the entire downloaded cover and both audio files matched their local SHA-256 digests, and range requests for both Episodes returned 206. This walkthrough did not test the new feed in a podcast app; an earlier separate test feed using the same real assets was confirmed in a podcast app by the administrator.

The new management bucket already had an enabled seven-day default multipart-abort rule; the guide's original command added a redundant rule. The guide now directs administrators to inspect existing rules first. The walkthrough used an existing Cloudflare API token rather than an interactive Wrangler login. The shell no longer had the separate CLI R2 credential, so the existing broader test copier credential was used for both CLI and copier. Worker secret files were prepared noninteractively, and CLI credentials were passed through environment variables rather than the guide's interactive prompts. Consequently, this run does not verify the interactive credential steps or the proposed least-privilege grants. The generated files and test workspace are under the ignored `.local-test/guide-live-checkout/`; the test Workers and buckets remain in the account.

At the time of those tests the plan had not been confirmed; the administrator has since confirmed that the test account is on a Free plan. The API billing endpoint was not independently accessible.

On 2026-11-09, the management and delivery Workers were deployed to isolated test Workers using separate test R2 buckets. The management endpoint rejected an unauthenticated request with HTTP 401 and accepted the configured token. A synthetic Show and cover were uploaded using the standalone CLI, and its published feed returned HTTP 200. A generated 52,801,454-byte MP3 was uploaded through the CLI's real multipart R2 path and accepted for future publication. Before release the public audio returned HTTP 404 and was absent from the feed. The alarm published it, observed 8.4 seconds after the requested time; its complete downloaded SHA-256 matched the source. HEAD, single byte ranges, suffix and open-ended ranges, unsatisfiable range and If-Range checks passed; repeated range requests reported cache MISS then HIT. One multi-range request returned multipart HTTP 206. A fresh workspace pulled the Show and Episode TOML without downloading audio.

Episode deletion then removed it from the feed and its public audio returned 404. Show deletion removed the public feed; both audio versions remained in the private management bucket. A separate real R2 conditional-copy test received HTTP 412 for an existing destination and confirmed the original contents survived. These observations do not establish Free-tier capacity or custom-domain behavior.

A separate published Show with a short generated MP3 was exported, deleted, restored under a hold and resumed. The feed again contained the original Episode GUID and the delivered audio matched the local source. The export contains references, not the source bodies, and its restore depends on retaining those R2 objects.

On that restored Show, two workspaces edited the same TOML independently. Pull installed the accepted remote version and preserved the conflicting local edit in `.bak`. The deployed `check --delivery` confirmed feed and audio HEAD responses and an audio range, `inventory` listed the registered sources, and cleanup preview with a one-day threshold reported no old candidates. The local implementation now checks up to eight Episodes concurrently while preserving report order; a 100-Episode mock test checks the concurrency bound and ordered missing-source errors. Targeted `recover` succeeded in each case, without losing accepted audio. This is an expected operational limit, not a Cloudflare outage: [Workers Caching](https://developers.cloudflare.com/workers/cache/limitations/#purge-rate-limits) always applies the Free-tier purge limits, and Cloudflare currently documents a token bucket refilling at five prefix-purge requests per minute with a capacity of 25 ([limits](https://developers.cloudflare.com/cache/how-to/purge-cache/#hostname-tag-prefix-url-and-purge-everything-limits)). The present publisher can issue more than one prefix purge per update; sustained bulk imports can exceed this rate. The archive test stopped before all audio was prepared; 100 published Episodes are not yet verified.

After recovery, a throttled run continued preparing the remaining audio. An uncontended `check` against the revised deployment returned HTTP 200 in 5,194 ms with 100 Episode records, including 44 that still lacked audio. This measures one request's wall time during preparation, not a controlled before/after comparison or a measurement with 100 published Episodes.

## Outstanding

Draft creation retries IDs that already exist in the local workspace. A new Show receiving a revision conflict is reidentified only after the CLI confirms an existing Show through its management snapshot. It moves the local Show directory, updates the Show and Episode TOML identities with original-file backups, and retries with a new operation ID. The local tests use a mock management/S3 server and also verify rollback when an Episode backup cannot be created. An uncertain response retains the original operation and IDs. Remote Cloudflare collision behavior remains unverified.

In a later real-account test, a separate fresh workspace submitted a Show draft with the ID of an already published synthetic test Show. The standalone CLI detected the remote collision, created a Show with a different ID and preserved the original draft as `show.toml.bak`. The pre-existing Show's revision, selected metadata, Episode records and served feed remained unchanged. This checks one Show collision on the deployed management Worker; it does not establish the deployed Episode collision path.

A second two-workspace deployed test created an Episode remotely after the other workspace had pulled the Show, then attempted to push a local Episode with the same ID from that stale workspace. The CLI returned `revision_conflict` and did not regenerate the ID; its original TOML backup and local marker file remained intact, and the already accepted Episode and Show revision were unchanged by the rejected request. Separately, a direct management request at the current revision attempted to create an existing Episode ID: the deployed Worker returned HTTP 409 `identity_conflict` with the explicit Episode ID path and left the existing Episode and revision unchanged. The rejected request's own staged test TOML was removed. These tests distinguish stale revisions from a confirmed current-revision collision; they do not exercise the CLI's automatic Episode reidentification against the deployed Worker.

A further deployed test exercised the CLI's Episode reidentification with a controlled local fixture: after pulling the current revision into a disposable workspace, the test removed the existing Episode's entry from that workspace's local baseline and replaced its local TOML with a synthetic new draft bearing the same ID. The standalone CLI submitted that draft to the real Worker, handled the collision, assigned a new ID and successfully created the new Episode. The draft backup and a local marker file were preserved, and the previously existing Episode record remained unchanged. Editing the baseline was test-only fault injection, not a normal user workflow or proof of how often a real collision occurs.

New local Show and Episode drafts also exclude IDs present in the workspace baseline or unresolved creation receipts, even when their local directories have been removed. Tests force such collisions, including a deleted baseline entry, and verify that another ID is chosen. Collision-driven ID regeneration uses the same exclusion. The local standalone-CLI integration test also forces a new Show ID to collide with an existing Show in a real local Durable Object: the CLI selects a different ID, retains the draft backup, and the original Show's revision remains unchanged. Other workspaces and external writers remain subject to the management Worker's creation and revision checks.

For an Episode create checked at the current Show revision, the Worker identifies an existing Episode ID with `identity_conflict` and the issue path `episodes.<episode-id>.id`; other identity errors and stale revisions do not carry that collision path. For a matching rejection of a newly created Episode, the CLI moves its local directory to a new ID, backs up the original TOML, rewrites the ID and retries the batch with a new operation ID. It reports the ID change, and preserves local media without copying it. Before moving either kind of draft the CLI writes a local recovery record; the next push rolls back an interrupted move before inspecting metadata. Recovery first compares every affected file against its original and rewritten bytes, and stops rather than overwriting a later edit. Tests simulate interruption, mixed file states and later edits; they do not simulate a machine power failure or filesystem durability guarantees. This assumes only one process modifies the workspace at a time. Stale-revision Episode conflicts still require pull; they are not automatically treated as collisions.

Before a metadata push, the CLI checks for saved uncertain mutation receipts for the affected Shows and directs the administrator to retry them first. Local tests verify that a second push does not submit another mutation, that retries retain the original request on an uncertain response, and that an explicitly rejected retry removes its receipt. This guard is workspace-local; it does not coordinate other computers or concurrent CLI processes.

The administrator may explicitly abandon an unresolved operation after confirmation. Local tests check that the pending receipt moves to an abandoned-record directory without overwriting an existing different record; this does not establish whether the remote operation was accepted.

The CLI also blocks workspace and remote mutations while an interrupted local ID change is unresolved. `operation recover-local` restores the files without contacting a server; `push` runs the same recovery before continuing. A standalone CLI test verifies that an audio upload is stopped before it inspects or uploads a file.

The design specifies machine-readable JSON mode for CLI outcomes. `castloop check --json` emits versioned reports including the full check result, errors and optional delivery probes; `castloop push --json` reports per-Show acceptance, delivery, uncertain receipts and local timezone normalization; `castloop operation retry <id> --json` reports acceptance separately from delivery and distinguishes uncertain responses. `show delete`, `episode delete`, `delivery migrate` and `delivery rollback` also accept `--json`, requiring `--yes` for confirmation. Show cover and Episode audio uploads accept `--json` and report uncertain operation IDs; `recover --json` returns the observed revision and result. `pull`, `show list`, `inventory`, `export`, `restore`, `restore-resume`, and `cleanup` also support JSON. Local setup and draft creation commands have human-readable output only. Do not rely on human-readable text as a stable structured interface.

CLI tests cover accepted changes with pending delivery for push, deletion, media upload and receipt retry: the accepted revision remains visible but the command exits with code 1 until delivery is complete. Human-readable output directs the administrator to check and, if necessary, recover the Show.

The standalone CLI has also been exercised against both real application Workers and their locally simulated R2 and Durable Object bindings.
