# Castloop TOML and RSS mapping

* **Author:** Akira Shimosako
* **Date:** 2026-11-07
* **Status:** Proposed schema for discussion. The user has chosen Apple's RSS guidance as the baseline. Field spellings, defaults, and extended tag scope below are not yet approved.

## Baseline

Use RSS 2.0 plus Apple's required and recommended metadata. Distinguish Apple requirements from Castloop's own publication rules. Incomplete TOML can still be stored in private management R2; publication errors must identify what is missing.

The mapping tables summarize [Apple's RSS guide](https://help.apple.com/itc/podcasts_connect/en.lproj/itcb54353390.html). Req = required, Rec = recommended, Cond = situational. The TOML names are Castloop proposals.

## Show metadata

### Administrator contact and error email

The user selected email as the desired administrator notification channel and requested administrator name/email in show TOML. Proposed spelling:

```toml
[admin]
name = "Example Administrator"
email = "admin@example.com"
```

These are private management fields, not automatically RSS fields. Keep public `author` separate: a show's presenter/publisher need not be the same displayed name as its administrator. Apple no longer recommends the `itunes:owner` contact tag and email; neither is required for the Apple baseline. See [Apple's technical update](https://podcasters.apple.com/4115-technical-updates-for-hosting-providers). Do not publish the administrator email by default. A future explicit public contact setting can reuse it with the administrator's intent, but it is not needed for error notification.

Cloudflare sending setup is installation configuration, not merely a syntactically valid TOML email. Verified destination addresses can receive free sends on all plans; the sender still needs a configured routing/sending domain. Accepted: email setup is optional and podcast hosting works without it, including domain-free deployments. Report missing email setup as notification unconfigured, not delivered or a podcast publication validation error. Administrator fields are private and not automatically included in RSS. See [error email design](./publication_errors_and_notifications.md#email-selected-by-the-user).

`generator` is generated by Castloop. RSS 2.0 independently requires the channel's title, description, and website link. Thus Castloop must include `website` in a complete publication candidate even though Apple labels it recommended. It must identify an actual corresponding website; do not silently substitute the XML feed URL. See the [RSS 2.0 specification](https://cyber.harvard.edu/rss/rss.html).

Accepted: the administrator supplies an existing homepage or other appropriate website URL in the MVP. The example `website` value below is supplied by the administrator and is independent of the podcast delivery domain. Automatic static show websites with browser audio playback are planned after the MVP; see the [roadmap](./concepts_brief.md#planned-after-the-mvp-static-podcast-websites). The future feature's custom-domain requirement remains open. Do not automatically overwrite the administrator's website link.

Proposed Castloop fields `id` and `publish` control identity and publication; they are not Apple RSS tags. `publish` defaults to `false`. Use boolean `explicit`; it is unrelated to `publish`. Show `explicit` should be provided before publication rather than inferred from the audio.

Propose `type = "episodic"` by default. Preserve category order and validate category/subcategory pairs against Apple's taxonomy. Check the show description's 4,000-byte limit in UTF-8; the episode description limit is 10,000 characters. Apply the RSS guide's field-specific limits rather than importing Apple Podcasts Connect form limits into RSS validation. Do not require arbitrary raw XML in TOML.

| `description` | `description` | Rec |
| generated audio duration | `itunes:duration` | Rec |

| `explicit` | `itunes:explicit` | Rec |
| `apple_title` | `itunes:title` | Cond |
| `episode_number` | `itunes:episode` | Cond |
| `season_number` | `itunes:season` | Cond |

Episode `id`, `show_id`, and `publish` are Castloop control fields. Propose inheriting the show's explicit flag when the episode omits it, while emitting the resolved value in RSS. Propose requiring description and an administrator-specified `published_at` for Castloop publication so the feed consistently includes recommended metadata. Interpret a local datetime through the stored episode timezone, initially defaulted from its show, as described below. These are application policy choices, not claims that every episode field is universally Apple-required.

Apple distinguishes full, bonus, and trailer episodes. Episode numbers are required for serial shows and optional for episodic shows. Castloop can represent these as `episode_type = "full"` by default and positive integer episode/season numbers where applicable. See [Apple's episode guidance](https://podcasters.apple.com/support/825-how-to-create-an-episode).

## Generated values

Do not ask the administrator to manually edit an enclosure URL, file size, MIME type, or duration in the metadata template. The CLI obtains those from the successfully uploaded media revision and delivery configuration. MP3 uses `audio/mpeg`; enclosure length is bytes, not playback seconds. Verify object existence without downloading every remote MP3 during a normal check.

Generate one episode GUID from its immutable UUID, for example `urn:uuid:<episode-uuid>`, with `isPermaLink="false"`. Preserve it across title edits, audio replacements, and domain migrations. Never derive it from a mutable media URL. Apple requires stable GUIDs and unique enclosure URLs between episodes. See [Apple's technical requirements](https://podcasters.apple.com/support/823-podcast-requirements). RSS specifies the non-permalink GUID attribute in its [GUID definition](https://cyber.harvard.edu/rss/rss.html#ltguidgtSubelementOfLtitemgt).

Store the administrator's `published_at` in TOML and convert the resolved time to RSS date formatting. Preserve it during unrelated edits. Future datetimes are accepted; the distinction between a future RSS timestamp and automatic scheduled publication is discussed below.

Generate XML declarations, namespace declarations, escaped text, and the Castloop generator value. Generate `lastBuildDate` when the feed changes. If optional Podcast namespace fields are emitted, include their namespace. Boolean `apple_block`/`complete` values map to `Yes` when enabled; they do not replace Castloop publication controls.

## Publication time and show timezone

Accepted: the administrator chooses each episode's publication datetime, including a future datetime. Each show has a default timezone, and each episode stores its own timezone in TOML. The administrator can omit it on first entry; the CLI fills it from the show default and saves it with the episode.

Propose `timezone = "Asia/Tokyo"` in both show and normalized episode TOML, using a named IANA timezone rather than the computer's local timezone. An initial episode input may contain only `published_at = 2026-11-14T09:00:00`; the CLI then adds its show's default `timezone`. Subsequent publication processing resolves that datetime using the episode value, not the current show value. Field spellings and sample values are proposals.

For comparisons, work with a resolved instant, not an unqualified local clock value. Generate an RSS timestamp with an explicit timezone offset or UTC. There is no new Apple-specific timezone tag in this proposal; `timezone` is Castloop configuration for interpretation and website presentation.

Reject unknown timezone identifiers. Do not silently choose an interpretation for ambiguous or nonexistent local times around daylight-saving changes; report the problem. The accepted disambiguation format is a technical detail to settle during drafting.

Accepted: a future datetime schedules automatic release, even when the CLI has exited. Until it is due, withhold the episode's RSS entry and keep its MP3 out of public delivery storage. Once due, make the MP3 available before publishing its feed entry. A delay of one or two minutes is acceptable; second-precise release is unnecessary. A future `pubDate` alone does not implement this behavior. A once-per-minute Cron Trigger is the current minimal candidate; see [scheduled publication](./concepts_brief.md#scheduled-publication). The target covers Castloop's public resources and caches, not external podcast apps' polling schedules.

Accepted: changing show timezone leaves existing episode TOML unchanged, preserving publication instants for published and reserved episodes. The planned website converts each episode instant to the current show timezone for display; regenerate static pages when show timezone changes.

Accepted normalization rule: if an update to an existing episode omits timezone, retain its authoritative stored timezone rather than copying a potentially changed show default. Only initially unspecified episode timezone needs the default. Save the normalized timezone in R2 TOML and include it in downloads. Explicitly changing an episode timezone is an episode update and must pass the normal validation and reservation-update rules; those scheduling details are still to be drafted.

## Artwork and serving

Apple requires show cover artwork. Its current cover specification accepts square RSS artwork from 1400 to 3000 pixels per side, preferring 3000, in JPG or PNG without transparency. See [Apple Show Cover specifications](https://podcasters.apple.com/support/5514-show-cover-template).

Accepted: store the show cover under `<show-id>/` in management R2 and refer to its filename in show TOML. Provide a Castloop command for cover updates. Propose the field spelling `artwork = "cover.jpg"`; this value identifies a file within the show's management prefix, not a local filesystem path or an external URL.

Upload cover images directly to management R2 using the same object client as MP3s. Validate the image in the CLI and copy an approved version to delivery R2. Generate its public URL for RSS. An invalid candidate remains in management storage and produces a clear publication error. Show validation failures preserve an existing valid public feed and the working cover/media that it references; an invalid replacement cover must not remove the working published cover.

For a cover replacement, generate a new delivery filename and URL, for example `cover-<revision>.jpg`, and update RSS accordingly. Apple's [RSS artwork guidance](https://help.apple.com/itc/podcasts_connect/en.lproj/itcb54353390.html) calls for changing both the filename and URL when updating artwork. The management filename may remain `cover.jpg`; the public revision name is generated. A content digest is one possible revision identifier, not a new required user-maintained field.

The command spelling `castloop show update-cover <show-id> cover.jpg` is a proposal. Define whether the command writes the current TOML filename itself or checks the existing filename during CLI design. A dedicated image generation or resizing service is unnecessary. Episode-specific artwork remains optional, and its asset-management scope is not yet selected.

Apple's feed submission checks include artwork and media availability; HEAD and byte-range support are delivery requirements, not TOML fields. `castloop check` should distinguish metadata readiness from public delivery checks and from Apple's approval. See [Apple's validation guidance](https://podcasters.apple.com/support/829-validate-your-podcast).

## Extended fields and MVP scope

Required and recommended fields should be representable. Optional fields need not all appear in a starter template. Keep common fields visible and document advanced fields separately.

Situational metadata is listed above so it is not mistaken for a universal publication requirement. Migration, Apple-specific blocking, completed-show status, and verification can be simple optional fields. Chapters/transcripts require agreed shapes and MIME handling before claiming support; recording their mapping does not mean those features are already in the MVP implementation. A minimal proposal is external URLs only, with no chapter editor, transcription job, or extra publishing service. Confirm this scope during drafting.

## Description formatting

Accepted: administrators write descriptions in TOML and may use a common, limited range of HTML formatting. This applies to show and episode descriptions and should remain usable by the planned static website.

Proposed allowlist:

| Purpose | Accepted tags |
| --- | --- |
| Paragraphs and breaks | `p`, `br` |
| Emphasis | `strong`, `em`, `b`, `i` |
| Lists | `ul`, `ol`, `li` |
| Links | `a` with an HTTPS `href` |

The tag list is Castloop's proposed supported input, not a claim that Apple or every podcast app renders all of it. Apple's RSS guide explicitly describes paragraph/list/link markup and CDATA handling; it does not establish identical rendering for every formatting tag. In particular, bold and italic display should be treated as client-dependent.

Keep the source description in TOML. Validate parsed HTML against the allowlist before publication and emit only approved markup. Unsupported elements or attributes should produce a field-specific validation error, with the source still saved under the agreed TOML storage policy. Omit scripting, event handlers, custom styles, and embedded media from the supported format. Use a small established parser/sanitizer rather than regex-based HTML handling; choose the dependency during implementation planning.

The show DO's feed renderer wraps HTML descriptions in valid RSS CDATA, safely handling any embedded CDATA terminator. CLI preflight can share parsing/validation helpers. CDATA preserves XML syntax but does not make arbitrary HTML safe for the later website. The website reuses the same approved formatting. Ordinary text remains acceptable; no Markdown conversion service or second rich-text source is introduced.

Example TOML input:

```toml
description = '''
<p>A conversation about <strong>small tools</strong>.</p>
<ul><li>Project updates</li><li>Lessons learned</li></ul>
<p><a href="https://example.com/notes/">Episode notes</a></p>
'''
```

## Example metadata inputs

These are proposed field spellings and illustrative values, not approved templates or published resources. The show artwork references a file within management R2, as the user has decided.

```toml
# show.toml
id = "s-8d3e1e41-3672-4eda-a3e7-84fa261808c5"
publish = false
title = "Castloop Notes"
description = "A weekly conversation about building small tools."
language = "ja"
timezone = "Asia/Tokyo"
explicit = false
author = "Example Host"
website = "https://example.com/podcast/"
artwork = "cover.jpg"
type = "episodic"

[[categories]]
name = "Technology"

[admin]
name = "Example Administrator"
email = "admin@example.com"
```

```toml
# episode.toml
id = "e-b74e8766-afd3-445f-a884-411b23a88e3e"
show_id = "s-8d3e1e41-3672-4eda-a3e7-84fa261808c5"
publish = false
title = "Building the first release"
description = "The first episode introduces the project."
published_at = 2026-11-07T12:00:00
# CLI adds timezone from the show when first saving this input.
episode_type = "full"
episode_number = 1
```

When the administrator sets both publication flags, incomplete metadata is saved but reported as unpublishable. The CLI owns media association; no local MP3 path or hand-maintained audio size is required in this example TOML.

Accepted after Goldfish review: if an episode fails publication validation during an update/publication operation, exclude it from the generated feed and remove its public delivery MP3 and cached copies, including when it was already published. Keep the saved management TOML/source MP3 and report why publication failed. A stale reservation must not later restore that invalid episode. The proposed read-only `castloop check` still reports issues without making these mutations.

Show validation failure is explicitly different: return the errors but preserve the last valid public feed, existing media, and working artwork. A new show with no valid public feed remains unpublished. Do not replace a valid feed with invalid show data or stop it for a show TOML editing mistake. Reject episode additions and updates while current authoritative show TOML is invalid, returning its validation errors instead of accepting the operation using an older show revision. Also block previously registered episodes whose release time arrives while show TOML is invalid; keep their MP3s private and omit their feed entries. After an accepted show correction passes validation, immediately start publishing overdue episodes that still satisfy both publication flags and their own metadata/media validation; leave future reservations pending. The episode release datetime and its stored timezone remain in episode TOML; show TOML supplies the initial default, not a mutable interpretation for existing episodes. No extra episode edit is needed to resume these eligible releases. TOML syntax errors must abort locally before upload and leave all R2/public resources unchanged; identity/path validation is a separate technical detail.

## Remaining decisions

Show artwork management is decided: a filename in show TOML, a source file under the show's management prefix, and a CLI cover-update command. Show `website` is an existing administrator-supplied homepage or other appropriate website. Limited HTML descriptions are accepted; the specific allowlist and sanitizer choice are proposals. Administrator-specified publication times, future times, automatic scheduled release with an acceptable delay of one or two minutes, and persisted episode timezones with show-default initialization and show-timezone website display are accepted. The user selected one show DO for full feed generation with SQLite derived state; no explicit publish command. Updates, due releases and repair invoke the same full-generation operation. Exact scheduler wiring, field/command names, optional chapters/transcripts, schema and identity/path validation remain drafting details. R2 stays authoritative and media uploads go directly from the CLI to R2.

## Episode unpublish

Accepted: updating an episode to `publish = false` removes its feed entry and deletes its MP3 from delivery storage, including invalidating cached copies. Retain management TOML and source audio. Existing reservations cannot republish it while false. This differs from deletion of management data. Stopping an already published show through `publish = false` requires explicit administrator confirmation, as defined below.

## Show unpublish confirmation

Accepted: changing a currently published show to `publish = false` must ask the administrator to confirm the show-wide stop. Only after approval, remove the show feed and public MP3s and invalidate delivery caches. Retain management TOML and source assets. Unpublished shows must block reservations from restoring public content. This is an intentional stop, distinct from preserving a valid public feed after show validation errors.

Propose showing the show ID/title and affected scope before confirmation, and cancelling the whole update without saving a false publication intent when declined. Noninteractive confirmation handling is a CLI detail to define; silence is not approval. A new unpublished draft does not trigger this published-to-unpublished confirmation.

## Mandatory local format check

Accepted: before sending TOML to R2 or performing any update side effect, the CLI parses it and reports syntax errors with useful location information. On a syntax error, stop processing and leave remote TOML, public feed/media, and reservations unchanged. This input-rejection rule precedes publication validation: missing titles or media in otherwise parseable metadata still follow the accepted save/error/publication rules.
